# 支付宝桌面 WAP 扫码安全复查（2026-10-06，未发布）

## 已核实

复查范围为本轮新增扫码入口、订单创建与恢复、官方支付宝 SDK 验签／查单、金额校验及余额履约。取证包括源码、已缓存 smartwalle/alipay v3.2.29 源码、真实测试 RSA 签名、隔离 SQLite 与实际仓储测试。没有访问商户接口、操作业务数据库或真实付款。

| 校验薄弱点 | 本轮处理与证据 |
| --- | --- |
| 参数重复时取首值／末值，可能产生解释差异 | 拒绝短入口重复 token、多余参数、超长／非法 query、非规范订单 ID；WAP 参数与 biz_content 重复键也拒绝。路由和 service 回归覆盖。 |
| HTTP 短链接暴露持有码权限；原回跳校验允许 Referer 扩展站点 | 新模式仅允许 HTTPS（本机回环开发除外），优先信任管理员 frontend_url；未配置时只使用请求 Host，不信任 Referer。创建订单前先校验，伪造 Referer／Host 的配置域名用例通过。 |
| 官方通知缺 app_id 时补配置，缺总额时使用其他金额 | 要求签名字段完整、app_id 等于配置、RSA2，并仅接受正数且最多两位小数的 total_amount；仍由 SDK 验证签名，不能通过补值获得身份。带真实测试签名的缺项／错商户／金额回退测试修复前失败、修复后通过；篡改金额／订单／签名被拒。 |
| 未验签 alipay_cert_sn 可触发 SDK 下载证书 | 当前接入只配置裸支付宝公钥，移除此不参与签名的提示字段，固定使用配置公钥验签。测试确认恶意证书序列号不触发任何网络调用；公钥轮换需管理员更新配置。 |
| 已付查询结果未核对原商户订单号，允许金额回退 | 仅接受原 out_trade_no、非空支付宝交易号及合法总额；测试用本地签名的 SDK 响应验证，无真实网络请求。 |
| 通用一分钱容差可接受 10 元订单回报 9.99 元 | 官方支付宝改为与网关两位金额精确匹配，不沿用容差。真实仓储测试修复前复现，修复后拒绝 9.99／10.01／10.001，余额不变；其他通道规则保留。 |
| 429 缺少禁止缓存头，Gin 重定向正文重复付款长地址 | Guard 在限流前设置 no-store／no-referrer；正常 302 仅 Location 含付款地址，正文为空。测试覆盖限流与失败响应。 |

以上是已经修复并有测试证据的校验缺口及防御加固，**不等于已证明攻击者可以伪造支付宝签名盗款，也没有证据证明生产曾被攻击**。通知应验签并核对应用、订单、金额，依据见[支付宝异步通知文档](https://developer.alibaba.com/docs/doc.htm?articleId=105285&docType=1&treeId=203)。前台回跳和扫码 GET 均不作为入账凭据。

## 幂等与状态

令牌由 crypto/rand 生成 32 字节，绑定保存的订单二维码，常量时间比较；错误令牌不披露订单信息。只有未过期 PENDING 订单可跳转，且固定 HTTPS 官方 WAP 网关，核对订单号、金额、商户和绝对期限。关闭设置不撤销已生成的有效订单。

新增真实仓储 SQLite 测试：16 个并发通知、随后三次重放，最后余额只增加 10 元，兑换码一条、充值成功审计一条、订单 COMPLETED；连续三轮通过。另有16并发履约租约测试只允许一个赢家。测试不使用余额存根，但 SQLite 测试不能替代生产 PostgreSQL 的并发验收。

取消／过期与手机付款可能竞态：扫码时检查状态无法撤销已经打开的支付宝页面。保留原验签通知和宽限恢复机制，对确实已付的订单按原状态规则处理，不能简单丢弃真实付款通知。

## 不知道／发布前待验

目前不能保证绝对“不会被黑”。尚不知道生产代理的 Host 限制、HTTPS、日志脱敏及实际商户配置是否满足要求。未配置管理员前端 URL 时，反代必须拒绝非本站 Host；建议明确设置本站 HTTPS 前端 URL。默认公共 IP 限流在 Redis 出错时放行，且私网 IP 可能跳过限流，不能把它当独立的抗攻击保证。代理日志应去除扫码 query，并避免记录完整 Location。

源码尚未提交／推送，无本轮新 SHA 的 CI、integration、安全和镜像结果；发布时必须逐项核对实际提交。生产由用户部署。真实支付宝 App 扫码是否无需本站登录、进入正确商户／金额，以及用户确认的小额实付后电脑自动成功且仅入账一次，仍按 [验收步骤](ALIPAY_DESKTOP_WAP.md) 完成，不能用本地 302 代替。
