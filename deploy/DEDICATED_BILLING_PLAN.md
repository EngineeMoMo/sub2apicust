## 二、建议的业务规则

采用独立的“包号预付费”计费模式，固定包号费用覆盖有效期内批准的使用权益。免扣依据是服务端有效包号绑定及本次请求归属，不能依据分组名称、is_exclusive、倍率零、客户端字段或仅仅Check无错误。

| 场景 | 期望行为 |
| --- | --- |
| 有效成员，Key绑定该账号获准的专属组，实际使用绑定账号 | 客户实扣0；正常计量包号用量，余额为0也允许 |
| 同一客户使用普通公共组 | 原有余额／订阅计费 |
| 名称叫专属组或is_exclusive=true，但没有包号权益 | 不享受免扣，保持原有规则 |
| 包号到期、撤销、删除、成员移除或资格／结构无效 | 拒绝新的包号请求，不偷偷改扣余额或转公共池 |
| 账号限流、无可用额度或包号安全上限耗尽 | 返回可解释的不可用／限额错误，不换公共账号免费顶上 |

同一账号关联同批成员多个专属组时，合法关联组都适用免扣，合并到同一包号计量。一个用户持有多个合法包号时，分别计量各自权益。

## 三、计费与计量必须分开

建议明确记录客户实扣金额、包号参考用量、Token／请求数、包号编号与权益周期。参考用量按确定的模型价格与计量规则计算，不依赖客户免扣倍率；它不是供应商真实账单，不能展示成已支付的上游成本。

包号结算时，数据库余额扣减为0，余额缓存不减、不触发假低余额通知；用户页面显示“包号内使用，实扣0”。Key防滥用窗口、包号用量与审计仍按独立计量值增长。前端总消费与导出、平台配额也要明确区分实扣和包号用量，避免普通付费消费报表混入参考金额。

入口只豁免有效包号请求的余额条件，仍检查用户／Key状态、Key到期、授权、模型权限及限额。后扣的正常事务、旧兜底及缓存更新都要按同一模式处理，不能只改数据库扣款一处；包号计量无法可靠落账时禁止进入无幂等兜底。

资格解析需要正向返回服务端包号凭证，包含绑定、原始用户／Key／组、选中账号、有效权益周期与计费模式。普通请求无凭证；绑定存在但不合法时返回拒绝。转发前复查实际账号与凭证一致，包号服务缺失或资格数据读取失败不能当免费通过。

异步记录使用显式参数传递凭证，不依赖worker原始HTTP context。已在有效期内获准并开始执行的请求按当时的包号模式结算；执行结束跨过到期／撤销不追改为余额收费。撤销后新请求和WebSocket新一轮重新检查。既有在途请求不承诺即时中止，任何开始前的检查与撤销之间仍需明确并发边界。

## 四、防止拆Key、跨组与高并发透支

1. **按包号合并限制**：同一绑定下所有成员／专属组／Key共享请求频率、并发槽和配置的用量窗口上限，成员可另加子上限。新建或删除Key、切组、重新授权均不重置总计数。不能只依赖Key额度或现有user×group RPM。
2. **在调用前约束**：允许模型清单、最大输入／输出及工具扩张范围、昂贵模型／生图权益由后台明确配置。数值按实际上游档位与业务流量确定，本轮不臆造统一数字。已有上游百分比快照有过期／未知状态，不能充当本站硬额度账本。
3. **并发下先占再结算**：至少原子获取包号共享并发槽；若承诺硬用量上限，需要估算占用／预留，完成后以实际用量结算、释放剩余，失败只释放未发生部分。崩溃及超时占用要可恢复，断流和客户端取消不能直接当零用量。仅异步完成后累计会有在途超限，不能宣称严格不超额。
4. **可靠账本与异常处理**：包号用量与去重在数据库同一事务落账，缓存用于加速并有校准及故障策略。超限、资格失败或无法取得可信计量／预留时拒绝新请求，不能悄悄放开。零价格／未知价格的模型要有独立Token或请求硬限，不能绕过用量限制。重试沿用同一业务结算身份；WS每轮、不同Key的独立执行分别计量，不能跨Key去重吞掉真实用量。
5. **生命周期不清账**：保留撤销／改绑／删除的历史隔离及消费；恢复Key、加成员、改别名不重置用量。续期是否新增总权益与日／周窗口重置分开，管理员有意调整才变化且留审计记录。
6. **识别共享但不过度承诺**：多IP同时高并发、突增用量等作为异常信号，可提示管理员、降速或暂停待处理；IP允许名单作为用户自选。正常多设备／移动网络不能仅凭换IP封禁。Key本身可转交，只能降低转售收益、发现异常，不能承诺彻底阻止同一身份私下共享；客户端自报设备ID不能作为可信身份。
